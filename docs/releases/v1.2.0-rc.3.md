# ForgeRelay 1.2.0-rc.3

ForgeRelay 1.2.0-rc.3 is the third release candidate for Config System v2. It keeps the same Config v2 product surface as rc.2 and hardens the remaining cross-platform release assertions exposed by the rc.2 Cloud CI matrix.

## What changed since rc.2

- CLI Project-scope regression fixtures now compare canonical filesystem roots instead of temporary-directory spellings.
- This covers both macOS `/var` → `/private/var` aliases and Windows short-path aliases such as `RUNNER~1` → the canonical long user path.
- The runtime Project identity implementation is unchanged: ForgeRelay continues to resolve and report canonical Project roots.

## Config System v2 scope

This candidate continues to include the full v1.2 Config System v2 surface:

- unified definition/resolver/provenance across General Config, External MCP, Language Servers, Lifecycle Hooks, and Subagent Profiles;
- precedence `runtime > project-local > project > user > built-in` subject to each field's legal scopes;
- Project identity and machine-private Project Local configuration;
- content-fingerprint demand refresh, last-known-good fallback, deletion semantics, and restart-required configured/applied reporting;
- explicit `config check`, `config sources`, `config explain`, and `config migrate` operator workflows;
- canonical `mcp.json`, `language-servers.json`, `hooks/*.json`, and `subagents/*.md` sources with v1.2 legacy compatibility;
- the shared Project executable-configuration trust seam with the v1.2 compatibility-allow policy;
- ForgeRelay-owned Skills remaining under the ForgeRelay config directory rather than being migrated into the open `.agents/skills` ecosystem.

## Release acceptance

The candidate is released only through the tag-triggered Linux/macOS/Windows Cloud CI matrix. Publication consumes the npm artifact built by the verified workflow and does not rebuild during publish.

The Config v2 packaged acceptance covers fresh initialization, direct v1.1-style upgrade without migration, explicit migration equivalence, diagnostics, reload/LKG/deletion, Project Local precedence, Project execution trust metadata, packaged runtime resources, and isolated server startup. Development and joint local acceptance continue to use the dedicated dev/test ports; production port 7676 is not part of this RC debugging flow.

Stable `v1.2.0` will only be promoted after an RC passes the authoritative multi-platform release gate and post-publication acceptance.
