# ForgeRelay 1.3.3

ForgeRelay 1.3.3 是一个 Agent 契约清晰度补丁，修复 Agent 在打开 Workspace 后可能把 ForgeRelay 错误判断为“只有只读能力”的问题。

## 修复：明确 Core tool 与 Capability discovery 的边界

`open_workspace` 会同时返回 Workspace bootstrap、Capability catalog 和 semantic feature fingerprint。此前模型可见文本虽然说明 `capabilityFingerprint.capabilities` 不是 `capability` Gateway 的可调用 registry，但仍可能让谨慎的 Agent 把 fingerprint / catalog 当成完整工具清单；由于其中不会逐项列出 `write`、`edit` 和 `bash`，Agent 可能据此错误拒绝写入或命令执行。

1.3.3 明确了三层契约：

- Host 当前的 `tools/list` snapshot 决定顶层 MCP Core tool 是否实际可调用。
- `minimal` / `full` 的常规 Core tool surface 仍是 `open_workspace`、`capability`、`close_workspace`、`read`、`write`、`edit`、`rename`、`delete` 和 `bash`。
- `capabilityCatalog` 只描述通过 `capability` Gateway 调用的非 Core Capability；`capabilityFingerprint` 只是 semantic feature fingerprint。Agent 不应因为 `write`、`edit` 或 `bash` 没出现在这两处就把 ForgeRelay 判断为只读。
- 如果 Host 的实际 tool snapshot 缺少当前 tool mode 应有的 Core tool，应优先判断为 Host MCP metadata 过期或不完整，并刷新 / 重连 integration。
- 模型可见标签同步收口为 **Capability catalog entries** 和 **ForgeRelay semantic feature fingerprint**，Relay 打开的 Workspace 使用同样术语。

## 兼容性

- 不改变 `capabilityFingerprint`、`capabilityCatalog` 或其他 MCP structured output 的字段结构。
- 不新增、删除或重命名 Core tool。
- 不需要 Config System v2 迁移，也不改变 Workspace、Git、文件写入或 Shell 权限。
- 如果 Host 确实缓存了旧的 `tools/list`，升级 ForgeRelay 本身不能强制 Host 刷新 schema；仍需要刷新或重连 MCP integration。

## 验证

本补丁覆盖 `open_workspace` 首次打开与重复打开的模型可见文本，并检查常规 Core surface、Capability catalog、semantic fingerprint 与 Host `tools/list` 的边界说明。相关 MCP contract、Workspace Relay routing 和 TypeScript 类型检查也纳入发布前验证。

正式发布继续使用仓库既有 release parity、打包验收、release proof 和 tag 驱动的跨平台云端 CI / npm / GitHub Release 流程。
