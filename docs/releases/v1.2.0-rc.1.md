# ForgeRelay 1.2.0-rc.1

ForgeRelay 1.2.0-rc.1 is the first release candidate for Config System v2. It puts General Config, External MCP, Language Servers, Lifecycle Hooks, and Subagent Profiles behind one resolver/provenance model while preserving a direct upgrade path from the v1.1 configuration surface.

## Config System v2

- Configuration precedence is `runtime > project-local > project > user > built-in`, with field-level scope rules defined centrally and runtime CLI overrides taking precedence over environment values.
- Project Local configuration is machine-private ForgeRelay state keyed by canonical Project identity rather than Workspace identity; it can override Project/User configuration without adding files to the checkout.
- Versioned JSON schemas ship in `schemas/v1/`, and supported sensitive fields can reference environment variables through definition-controlled `${ENV_NAME}` interpolation without exposing resolved secrets in normal provenance or diagnostics.
- `forgerelay config check`, `config sources`, and `config explain <logical-path>` provide secret-safe validation, source inspection, winner/shadowing details, reload policy, and execution-effect diagnostics.

## Canonical configuration and reload behavior

- External MCP uses `mcp.json`; Language Servers use `language-servers.json`; Lifecycle Hooks use one `hooks/*.json` file per Hook; Subagent Profiles use `subagents/*.md`.
- Canonical User, Project, and Project Local sources refresh on demand from content fingerprints rather than mtimes. A previously valid source that becomes invalid keeps its in-process last-known-good value until repaired; deleting the source removes that contribution.
- Long-lived Language Service generations retire when their effective executable/configuration changes. Restart-required General Config reports configured versus applied state and never silently restarts ForgeRelay.

## Setup and migration

- Basic `forgerelay init` now asks only for required project roots and connection mode, with mode-specific network details when necessary. `init --advanced` contains the common advanced choices such as port, Command Shell Runtime, Runtime Shell Instructions opt-in, managed Language Servers, and Agent-managed installation permission.
- Runtime Shell Instructions are disabled by default. `init --force` updates setup-owned fields without erasing unrelated advanced configuration and is not an implicit migration command.
- `forgerelay config migrate` is explicit and user-driven. `--dry-run` previews the plan; applied migration preserves backups, uses atomic writes, and migrates only ForgeRelay-owned formats.
- ForgeRelay does not import private Claude, Codex, Cursor, or other product configuration, and it does not move ForgeRelay-owned Skills into the open `.agents/skills` ecosystem.

## Compatibility

- Existing v1.1-style ForgeRelay configuration remains directly readable in v1.2.x with deprecation diagnostics, so upgrading the package does not require an immediate migration.
- Canonical same-scope sources shadow the corresponding legacy adapters. v1.3.x will strengthen removal warnings, and the documented legacy parser/path boundary is v1.4.0.
- Subagent Profiles are canonical under `subagents/`; legacy `agents/` remains a compatibility source during the v1.2 window.

## Security boundary

- Allowed roots remain filesystem/Workspace authority; they are not Project Trust approval.
- Project Hooks, stdio External MCP, Project Language Servers, and Project Subagent Profiles now pass through one Project execution trust seam. The v1.2.0 policy is intentionally `compatibility-allow`; this RC does not claim a full interactive Project Trust approval UI.
- Credentials remain outside the ordinary Config Resolver, and resolved sensitive values are excluded from normal operator output.

## RC verification

This release candidate is shipped only through the tag-triggered release workflow. Linux, macOS, and Windows Cloud CI verify the tagged tree, build the npm package once, and publication consumes that verified artifact without rebuilding it. The Config v2 packaged acceptance exercises fresh initialization, a direct 1.1-style upgrade without migration, explicit migration equivalence, diagnostics, reload/LKG, Project Local behavior, the trust seam, and isolated packaged server startup on the dedicated acceptance port.

Stable `v1.2.0` will not be promoted from this RC if release acceptance finds a blocker; a subsequent RC will carry the fix instead.
