# ForgeRelay 0.6.0-rc.1

This is the first release candidate for the next ForgeRelay line. It contains all work since `v0.5.6`; the intermediate `0.5.7` metadata was never tagged or published, so its changes are included here rather than treated as a separate public release.

The main goal of this RC is to validate the end-to-end ChatGPT MCP App lifecycle before calling the 0.6 line stable. The core MCP tool surface remains intentionally small; most of the work is in Host lifecycle, App rendering, Skill loading, deployment routing, and long-running process behavior.

## What changed

### Unified Workspace + Activity experience

ForgeRelay now treats one Host Turn as one coherent panel. The Workspace Summary stays visible above a separately collapsible Activity Panel, while operations in that turn update the same Activity surface instead of producing a disconnected sequence of cards.

Activity data is still owned by ForgeRelay's durable audit/query layer rather than by the UI. The App loads normal summaries first, requests operation detail lazily, and can stream durable Bash output separately. Follow-up control calls for the same Bash process continue updating the existing semantic Activity instead of creating duplicate top-level Activities.

Host Turn identity is also more robust. ForgeRelay prefers Host conversation metadata when available, falls back to the MCP transport session, and finally to the current MCP connection. This makes the lifecycle observable in MCP Inspector and other Hosts that do not provide OpenAI-specific conversation metadata while keeping Workspace state isolated.

### Virtual Skill namespace

Skills are now advertised by name instead of exposing their real filesystem paths to the Agent. A Skill is loaded with:

```text
read(path="skills://<name>")
```

After that Skill is loaded, its bundled files are available through:

```text
skills://<name>/<relative-path>
```

Legacy absolute Skill paths remain readable for stale Host metadata during the compatibility window, but new bootstrap metadata no longer advertises them. Skill diagnostics shown to the Agent also redact local path details.

### Public deployment routing

`publicBaseUrl` now accepts either one routed public URL or an ordered list. Route prefixes are preserved end to end, the first URL remains canonical, every configured hostname joins the derived Host allowlist, and the complete ordered URL list participates in MCP App resource identity and CSP metadata.

This RC also fixes OAuth and debug paths that previously risked collapsing a routed public URL back to its bare origin.

### More efficient long-running Bash waits

When a command has already returned a `processId`, Agents can now perform one bounded wait with the existing process:

```text
bash(action="process", processId=123, yieldTimeMs=60000)
```

If the process finishes during that window, ForgeRelay returns the final result immediately. If the window expires first, the same `processId` is returned and the process keeps running. This is independent of `timeoutMs`, which remains the actual execution deadline that may terminate a process.

Explicit waits now behave this way even when the command is continuously producing buffered output, removing a common reason for Agents to fall into repeated short polling.

### Better local Host debugging

The repository now includes a dedicated MCP Inspector workflow on `127.0.0.1:7677`. It exercises the real HTTP/OAuth/MCP App path while keeping the normal product port separate. Debug configuration, logging, App metadata, and Inspector transport-session behavior have corresponding regression coverage.

## Release-candidate channel

RC tags use the normal release verification path but do not move the stable npm channel:

- Git tag: `v0.6.0-rc.1`
- npm version: `0.6.0-rc.1`
- npm dist-tag: `next`
- GitHub Release: marked as a prerelease

Install this RC explicitly with:

```bash
npm install -g @akira-tl/forgerelay@next
```

Stable installs that use `latest` remain on the previous stable release until the 0.6 line is promoted.

## What to validate in RC1

The most useful RC feedback is around the real Host lifecycle rather than isolated rendering snapshots: repeated tool calls in one ChatGPT turn, switching or reopening Workspaces, long-running Bash commands that return and later complete, lazy Activity detail/output loading, `skills://` loading, and public tunnel/reverse-proxy deployments with routed or multiple public base URLs.

Please report any case where the Agent-visible result, durable Activity history, and rendered panel disagree about the state of the same operation. Those boundary mismatches are the main reason this release is being published as an RC rather than directly as stable 0.6.0.
