# ForgeRelay 1.1.0

ForgeRelay 1.1.0 makes image-bearing MCP results a first-class, bounded transport path without turning ForgeRelay into an image store or an autonomous external-MCP orchestrator.

## Added

- The existing `read` tool now returns PNG, JPEG, WebP, and GIF files as standard MCP `ImageContent`, recognized by file signature rather than extension. Image bytes are forwarded unchanged, mixed text/image bulk Reads keep input order, and text `offset` / `limit` arguments are rejected for images.
- User-configured external MCP servers are available through the workspace-scoped `mcp.external` Capability. Direct upstream `ImageContent` is forwarded to the Host while path-, URL-, and resource-only results remain references by default.
- `ExternalMcpBeforeForward` and `ExternalMcpAfterForward` Hooks provide an explicit structured transform seam for server/tool-specific adaptation. They cannot retarget the configured server/tool, and transformed media is revalidated before delivery.

## Changed

- Workspace Relay preserves image content unchanged from Execution ForgeRelay to Gateway ForgeRelay and applies the Gateway's own media budget before Host delivery.
- Media is transient MCP content, not an automatic Artifact. The default decoded-media budget is 20 MiB per tool result, including aggregate media in bulk results. Oversize media fails explicitly rather than being truncated, resized, transcoded, or silently dropped.
- Activity/Audit, structured output, UI state, logs, and Workspace state keep bounded media metadata such as MIME type and decoded byte size instead of image base64.

## Security and authority boundaries

- ForgeRelay does not implicitly fetch or `read` paths, URLs, or resource references returned by external MCP servers. Any path-to-image conversion remains an explicit Agent `read` or an explicitly configured transform Hook.
- External MCP credentials and arbitrary media payloads are excluded from persisted Activity/log state. External servers and transform commands retain only the operating-system/network authority explicitly configured by the user; Capability routing does not imply additional sandboxing.

## Verification

The release is gated on the complete local test/build/typecheck/architecture suite plus real HTTP/OAuth/MCP acceptance on 7677, real 7677 → 7678 Workspace Relay acceptance, deterministic external-MCP and transform-Hook acceptance, package verification, and a real ChatGPT Host vision check of the deterministic PNG sentinel. Port 7676 is not used for acceptance.

The `v1.1.0` tag is created only after those local gates pass. The tag then runs the authoritative Linux, macOS, and Windows Release workflow before npm publication and GitHub Release creation.
