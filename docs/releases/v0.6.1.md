# ForgeRelay 0.6.1

ForgeRelay 0.6.1 adds Workspace Relay: one ForgeRelay can now act as the Host-facing Gateway while another ForgeRelay owns the actual Workspace, filesystem, process, capability, Hook, Skill, and Activity state. The Host continues to use the normal ForgeRelay MCP tools and a Gateway-issued Workspace ID; remote addresses, SSH routing, and credentials stay outside the model-facing Workspace contract.

## Highlights

### Authenticate and register remote ForgeRelay instances

`forgerelay auth` now authenticates a remote ForgeRelay and registers it under a local alias in one step.

Direct connection:

```bash
forgerelay auth 10.11.12.13:7676 --alias workstation
```

By default the owner token is requested through hidden terminal input. Automation and controlled test environments can provide it explicitly:

```bash
forgerelay auth 10.11.12.13:7676 --token "$FORGERELAY_OWNER_TOKEN" --alias workstation
```

If the service is only reachable through SSH, `-J` selects the SSH transport. The final item is the machine ForgeRelay logs into; earlier items become the ProxyJump chain. The service target is interpreted from the final SSH machine's network view.

```bash
forgerelay auth \
  -J user@jump.example,user@workstation \
  127.0.0.1:7676 \
  --ssh-auth \
  --alias workstation
```

A single SSH destination works the same way without ProxyJump:

```bash
forgerelay auth -J user@workstation 127.0.0.1:7676 --ssh-auth --alias workstation
```

`--ssh-auth` asks the final SSH machine for its ForgeRelay owner token, returns that secret only to the initiating process, and then uses the same CLI authentication route as direct authentication. The owner token is not stored in the remote record and is not used as the normal MCP bearer token.

Remote registrations can be inspected or maintained with:

```bash
forgerelay auth list
forgerelay auth test workstation
forgerelay auth rename workstation desktop
forgerelay auth remove desktop
```

### Open a remote Workspace through the normal MCP surface

Once a remote is registered, the Agent only needs the alias:

```text
open_workspace({
  path: "/home/akira/project",
  relay: "workstation"
})
```

The path is interpreted and validated by the execution ForgeRelay, not by the Gateway's local filesystem rules. The Gateway returns its own opaque `rws_...` Workspace ID and uses that ID for all later calls.

The following operations now route through the execution ForgeRelay for a relayed Workspace:

- file read, write, edit, rename, delete, and bulk preflight semantics;
- Bash foreground commands, returned/background processes, waiting, input, interruption, and durable full output;
- optional capabilities, including code intelligence and Hook inspection;
- Workspace Skills and capability guides;
- Workspace close/finalization semantics;
- Activity Panel Host Turns, snapshots, lazy detail, and durable Bash output queries.

Hooks execute only on the execution instance for relayed operations. The Gateway does not duplicate filesystem/process side effects or remote Activity audit facts.

### Stable identity across reconnects and restarts

Relay identity is based on the stable remote instance ID plus the execution-side Workspace ID, not on a display alias, network address, SSH process, or temporary forwarding port.

That means an existing `rws_...` can survive:

- a Gateway restart;
- access-token expiry and refresh-token rotation;
- re-authentication of the same remote instance at a different service address;
- renaming the local remote alias;
- teardown and recreation of an SSH tunnel on a different random local port.

Relayed route state is persisted separately from runtime transport state. Concurrent Gateway/CLI sessions use lock-protected read/modify/write updates and atomic file replacement so one session does not erase another session's remote or Workspace records.

### SSH is transport, not a second relay protocol

ForgeRelay does not implement a custom jump-host protocol. With `-J`, it delegates connection and ProxyJump behavior to the system SSH client and creates a temporary loopback-only local forwarding endpoint for each remote operation.

There is no "try direct, then silently fall back to SSH" behavior:

- no `-J` means direct transport;
- `-J` means SSH transport;
- a failed route fails explicitly.

The intermediate SSH hosts do not need ForgeRelay installed. Only the final execution machine needs a ForgeRelay service reachable from that machine's network view.

### Remote Activity stays execution-owned

For a relayed Workspace, `activity_panel` starts the real Host Turn on the execution ForgeRelay. The Gateway only routes Activity queries and maps execution-side Workspace identity back to the Gateway `rws_...` identity.

This includes:

- lightweight `activity_snapshot` summaries;
- `activity_detail` lazy detail;
- complete `activity_output` Bash output;
- late `bash_result` Activities after a returned background process finishes;
- isolation between separate Host conversation scopes even when they share the same remote and Workspace.

Remote targets, SSH routes, temporary ports, owner tokens, access/refresh tokens, and execution-side `ws_...` identifiers are not exposed through the relayed Host Activity surface.

## Failure behavior and security boundaries

Workspace Relay intentionally fails closed at routing boundaries:

- an unknown alias does not fall back to local execution;
- a path rejected by the execution ForgeRelay is not retried against the Gateway filesystem;
- bad or expired credentials follow the existing refresh/authentication rules and do not switch remotes;
- an offline remote reports a remote connection failure;
- an execution-side Workspace that no longer exists is reported as invalid and is not silently reopened by path;
- SSH command/tunnel failures do not trigger a direct-network fallback.

SSH forwarding uses random local loopback ports and does not persist those ports as Workspace identity. SSH-routed Workspace Relay currently expects the forwarded ForgeRelay service itself to use HTTP inside the SSH transport rather than presenting an HTTPS certificate for the temporary `127.0.0.1` endpoint.

## Validation

The `v0.6.1` candidate was validated with deterministic dual-instance tests using independent configuration directories, state directories, and allowed roots. Coverage includes direct transport, single-target SSH, multi-hop SSH, all three owner-token input modes, file mutations and bulk preflight, process lifecycle and durable output, capabilities and Skills, route recovery, token refresh, SSH tunnel rebuild, Host Activity forwarding, explicit failure/no-fallback behavior, local Workspace regression, and the existing OAuth browser route.

The final release gate includes the full TypeScript check, complete test suite, production build, packaged CLI smoke check, and npm package dry run.
