# ForgeRelay 1.2.0

ForgeRelay 1.2.0 is the stable release of Config System v2. It promotes the accepted `1.2.0-rc.1` behavior without introducing additional product changes after RC acceptance.

## Config System v2

- Configuration precedence is `runtime > project-local > project > user > built-in`, with legal scopes, merge behavior, reload policy, sensitivity, defaults, and execution effects defined centrally.
- General Config, External MCP, Language Servers, Lifecycle Hooks, and Subagent Profiles resolve through one model with provenance and strict validation.
- Project Local configuration is machine-private ForgeRelay state keyed by canonical Project identity rather than Workspace identity, so linked and managed worktrees for one Project share the same local overrides.
- Versioned JSON schemas ship in `schemas/v1/`. Supported sensitive fields may use definition-controlled `${ENV_NAME}` interpolation while resolved values remain excluded from normal diagnostics and provenance.
- `forgerelay config check`, `config sources`, and `config explain <logical-path>` provide operator-facing validation, source inspection, effective-value provenance, shadowing, reload policy, and execution-effect diagnostics.

## Canonical sources and reload behavior

- External MCP uses `mcp.json`; Language Servers use `language-servers.json`; Lifecycle Hooks use `hooks/*.json`; Subagent Profiles use `subagents/*.md`.
- User, Project, and Project Local sources refresh on demand from content fingerprints rather than filesystem mtimes.
- Invalid edited sources retain their in-process last-known-good revision where one exists. Deleting a source is intentional absence and removes that contribution instead of retaining LKG.
- Restart-required General Config distinguishes configured from applied values. Long-lived Language Service and External MCP generations retire safely so in-flight work can finish while new work uses the replacement generation.

## Setup and migration

- Basic `forgerelay init` asks only for required project roots and connection mode. `init --advanced` contains the common advanced choices such as port, Command Shell Runtime, Runtime Shell Instructions opt-in, managed Language Servers, and Agent-managed installation permission.
- Runtime Shell Instructions are disabled by default. `init --force` updates setup-owned fields without erasing unrelated advanced configuration and is not an implicit migration command.
- `forgerelay config migrate` is explicit and user-driven. `--dry-run` previews the plan; applied migration creates backups, uses atomic writes, and migrates only ForgeRelay-owned formats.
- ForgeRelay does not import private Claude, Codex, Cursor, or other product configuration, and it does not install or migrate ForgeRelay-owned Skills into the open `.agents/skills` ecosystem.

## Compatibility

- Existing v1.1-style ForgeRelay configuration remains directly readable throughout v1.2.x with deprecation diagnostics, so upgrading does not require an immediate migration.
- Canonical same-scope sources shadow the corresponding legacy adapters. v1.3.x strengthens removal warnings; the documented legacy parser/path removal boundary is v1.4.0.
- Subagent Profiles are canonical under `subagents/`; legacy `agents/` remains a compatibility input during the compatibility window.
- Credentials remain outside ordinary Config Resolver precedence and continue to use machine-private credential storage.

## Security boundary

- Allowed roots remain filesystem and Workspace authority; they are not Project Trust approval.
- Project Hooks, stdio External MCP, Project Language Servers, and Project Subagent Profiles pass through one centralized project-execution trust seam.
- The v1.2.0 policy is intentionally `compatibility-allow`. Full interactive Project Trust approval and enforcement remains a later v1.2.x feature rather than being implied by this release.
- Project execution trust and elevated-runtime protection remain independent gates.

## Release acceptance

`1.2.0-rc.1` completed the stable-release acceptance contract before this promotion. The authoritative tag-only workflow verifies Linux, macOS, and Windows independently, builds one npm tarball, and makes all packaged platform acceptance consume that same artifact. Publication reuses the verified artifact without rebuilding it.

The accepted RC passed fresh initialization, a direct 1.1-style upgrade without migration, explicit migration equivalence, Config diagnostics, reload/LKG behavior, Project Local behavior, the project-execution trust seam, packaged server startup on the isolated `7678` acceptance port, macOS filesystem/path acceptance, and Windows path/process/native-shell acceptance for PowerShell 7, Windows PowerShell 5.1, and `cmd.exe`.

The released RC package was also downloaded and installed again from the public npm registry after publication, and the registry artifact passed the packaged Config v2 lifecycle acceptance. No unresolved release blocker remains between the accepted RC and this stable promotion.
