# ForgeRelay 1.2.0-rc.2

ForgeRelay 1.2.0-rc.2 is the second release candidate for Config System v2. The first RC tag exposed two cross-platform verification defects before publication; this RC fixes those portability issues without changing the Config v2 runtime contract.

## Cross-platform release fixes

- Generated Config schema freshness checks now treat CRLF and LF checkout line endings as equivalent while still rejecting semantic schema changes. This fixes the Windows Cloud CI false positive that marked every generated `schemas/v1/*.schema.json` file stale.
- Project identity regression tests now compare canonical filesystem realpaths. This matches the existing runtime contract on macOS, where temporary paths under `/var` resolve canonically under `/private/var`.
- Both fixes have focused regression coverage and preserve the existing Linux behavior.

## Config System v2 candidate

The Config v2 behavior remains the same candidate contract introduced for v1.2: unified `runtime > project-local > project > user > built-in` resolution and provenance; canonical External MCP, Language Server, Hook, and Subagent sources; Project Local private configuration; content-fingerprint hot reload with last-known-good behavior; explicit migration; `config check/sources/explain`; and the shared Project execution trust seam with the v1.2.0 `compatibility-allow` policy.

Existing v1.1-style ForgeRelay configuration remains directly readable in v1.2.x with deprecation diagnostics. Explicit migration is user-driven and limited to ForgeRelay-owned formats; private configuration from other Agent products is not imported.

## RC verification

The RC is published only after the tag-triggered Linux, macOS, and Windows Cloud CI matrix passes. The workflow builds the npm package in the verified CI job and the publication job consumes that exact artifact without rebuilding it. Config v2 packaged acceptance covers fresh initialization, direct v1.1-style upgrade, explicit migration equivalence, diagnostics, reload/LKG, Project Local behavior, the Project execution trust seam, and isolated packaged startup using the development acceptance topology.

The failed `v1.2.0-rc.1` workflow stopped before package/release publication, so no rc.1 npm or GitHub Release artifact is being replaced or rewritten.
