# ForgeRelay 0.6.2

ForgeRelay 0.6.2 introduces **Composite Workspace**: one Host-facing Workspace can now coordinate several explicitly named ForgeRelay Workspaces at the same time without pretending that their filesystems, Git state, processes, Hooks, Skills, or Activity facts are merged.

A typical Composite Workspace can keep ordinary source work on one machine while sending GPU or high-performance jobs to another ForgeRelay through Workspace Relay. The Agent keeps one `cws_...` top-level identity and explicitly selects the member that owns each operation.

## Highlights

### One Workspace lifecycle for ordinary and composite work

Composite Workspace is a first-class Workspace kind on the existing `open_workspace` surface. It does not introduce `open_composite_workspace` or a second Host lifecycle.

A Composite Workspace may be created before all of its execution environments are ready:

```text
open_workspace({
  kind: "composite",
  name: "research-project"
})
```

The result has its own persistent `cws_...` identity and may initially contain zero members. Opening or resuming that identity always tells the Agent that it is composite and returns the lightweight member topology even when normal bootstrap context is deduplicated.

Composite Workspace itself has no synthetic filesystem root. Each member remains a real ordinary, managed-worktree, or relayed Workspace with its own execution authority.

### Explicit named members

Members carry a stable name plus an Agent-facing purpose, for example:

```text
research-project
├─ code
│  purpose: source control, editing, ordinary analysis
│  workspace: local checkout
└─ compute
   purpose: GPU training and high-performance processing
   workspace: relayed ForgeRelay
```

Members can be added from an existing Workspace handle or from the same Workspace definition fields already used by `open_workspace`, including Workspace Relay definitions.

Member purpose is descriptive only. ForgeRelay does not route by tool type, hardware role, availability, or previous success. Every Composite operation explicitly names its member, so execution ownership is visible and deterministic.

### Local and remote execution under one Composite identity

Core filesystem, capability, Bash/process, and Codex-compatible operations now resolve through the selected Composite member while preserving the Composite Workspace ID as the Host-facing handle.

Conceptually:

```text
read({ workspaceId: "cws_...", member: "code", ... })
bash({ workspaceId: "cws_...", member: "compute", ... })
```

The selected member can be:

- a normal checkout Workspace;
- a managed ForgeRelay worktree;
- a Workspace Relay `rws_...` whose execution is owned by another ForgeRelay.

Remote member failures fail closed. ForgeRelay never falls back to another member or to the Gateway filesystem.

The Codex compatibility surface follows the same rule: `apply_patch`, `exec_command`, and `write_stdin` now use the same local/relay member resolution path rather than bypassing Workspace Relay.

### Member-specific bootstrap without context explosion

Composite topology is lightweight and always visible, but project bootstrap remains member-specific.

When the Agent needs the instructions and capabilities for one member, it reopens the same Composite Workspace while naming that member and uses the normal `context="auto" | "full" | "none"` policy. Existing context fingerprints continue to prevent repeated AGENTS/Skills/capability-guide injection.

This avoids merging instructions from several machines into one large or conflicting bootstrap while still making every available member discoverable.

### One Composite Activity timeline

A Composite Workspace has one Host-facing Host Turn / Activity Panel. Operations from different members appear together with their member name, for example:

```text
code     read   src/train.py          done
compute  read   dataset.json          done
compute  bash   training command      returned
code     read   README.md             done
compute  bash_result                  done
```

This is presentation aggregation, not a second audit store.

Local member Activity remains owned by the real local member Workspace. Remote member Activity, process state, durable Bash output, Hooks, filesystem changes, and audit facts remain owned by the execution ForgeRelay. The Gateway only aggregates and routes snapshot/detail/output queries.

### `close_workspace` dissolves Composite relationships safely

There is no separate dissolve API. Calling `close_workspace` with a Composite Workspace ID dissolves the Composite identity and its membership definitions.

Dissolution intentionally does **not**:

- close member Workspace handles;
- finalize managed worktrees;
- commit or merge member repositories;
- interrupt running member processes;
- delete member files;
- remove Workspace Relay routes or remote authentication records.

After dissolution, the former `cws_...` cannot be reopened, while its member Workspaces remain independently usable.

### Better isolated multi-instance debugging

`npm run dev` already supported relocating interactive debug configuration with `FORGERELAY_DEBUG_CONFIG_DIR`. In 0.6.2 the launcher also derives the displayed debug endpoint from that selected `config.json` instead of assuming every debug instance uses port 7677.

This makes multi-instance debugging straightforward: separate configuration directories can independently define their own config, state, worktree root, credentials, and port.

The Composite Workspace acceptance run used two real HTTP/OAuth/MCP instances:

```text
Gateway   127.0.0.1:7677
Execution 127.0.0.1:6768
```

Each instance used an isolated temporary configuration/state directory. The acceptance exercised local and relayed members, concurrent member work, remote Bash completion, aggregated Composite Activity, Codex-compatible relay routing, and dissolution while preserving both member Workspaces.

## Compatibility and boundaries

Ordinary Workspace behavior is unchanged when Composite Workspace is not used.

Composite Workspace deliberately does not provide:

- automatic file or dataset synchronization;
- automatic Git revision synchronization;
- automatic member selection or load balancing;
- failover between members;
- cross-member transactions;
- automatic remote discovery.

Workspace Relay remains responsible for *where one member executes*. Composite Workspace is responsible for *which explicitly named Workspace participates in one Host-facing working context*.

## Validation and release gate

Before preparing the release, the 0.6.2 implementation was exercised through targeted TypeScript/server/UI regressions plus real dual-instance HTTP/OAuth/MCP black-box acceptance on isolated ports and configuration/state directories. The temporary services and credentials were removed after acceptance.

The pushed `v0.6.2` tag is still subject to the repository's authoritative GitHub Actions release gate. Linux, macOS, and Windows cloud CI must all pass before the verified npm artifact is published and the GitHub Release is created.
